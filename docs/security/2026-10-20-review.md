# SuggFeed combined security and attack-resilience review

Date: 20 October 2026 (Asia/Manila). Source revision: `7e062db`.

This is an evidence-based engineering review, not a penetration-test certificate or legal opinion. No application fixes, provider settings, data resets, invitations, emails, or database mutations were performed. The report and sanitized metadata evidence are the only repository changes.

This report combines both supplied review requests. Sections 1–10 cover the security engineering areas and ranked findings. Section 11 maps all 13 requested attack families to applicability, observed defenses, gaps, fixes and detection. The same weakness retains its original finding ID rather than being counted again under multiple attack types.

## 1. Scope, missing information, and evidence

SuggFeed is a shared service for school feedback: ideas, voting, comments, moderation, progress, invitations, school membership, enrollment eligibility, private form answers and attachments. The active application is Express/Eta/TypeScript on Vercel with Supabase Auth, Postgres and private Storage. Platform operators, school admins, moderators, students and anonymous visitors have different authority. Identifiable school feedback can contain sensitive educational or health information; Philippine Data Privacy Act obligations require institutional/legal assessment.

The user confirmed there is no separate staging environment and subsequently permitted testing the hosted database. This review chose local disposable databases for active checks and only read-only hosted security metadata/advisors. Plans to erase a database later do not eliminate account/email or credential sensitivity now.

Outstanding information:

- Normal/peak requests per second, school NAT patterns, provider spend caps, origin exposure, edge connection/body timeouts and database statement timeouts were not supplied. Do not choose production rate limits or claim DDoS resistance from local tests alone.
- Supabase password length/expiry/rate settings, OAuth console configuration, deployed Edge versions, JWT signing/rotation settings, backup access/restore evidence, and exact Vercel-to-Supabase environment alignment still need confirmation.

## 2. Threat model

### Assets and actors

- Assets: account sessions/refresh tokens, platform authority, school membership/rosters, private answers/files, unpublished ideas, moderation notes, audit evidence, provider credentials, delivery reputation and hosting/database budget.
- Actors: anonymous visitor, signed-in student, user from another school, moderator, school admin, platform insider, stolen account, malicious dependency/build action, compromised provider credential.

```text
Browser (untrusted identifiers, form data, local auth tokens)
  | HTTPS; server cookie; same-origin checks
  v
Vercel edge/proxy [external WAF settings unknown]
  v
Express: session decryption -> provider identity verification
  -> platform checks OR school resolution/membership/eligibility
  -> staff MFA -> route authorization/input validation
  |                     |
  | scoped service reads| service-only tenant_rpc + tenant_executor RLS
  v                     v
Supabase Postgres [tenant rows / global accounts / server-only settings]
  |
  +-> private Storage [scoped reservations -> validation -> authorized download]
  +-> authorized jobs -> Resend [verified address, idempotency, consent]

School admin -> private visual editor -> same-origin fictional preview frame
GitHub source/actions -> Vercel build -> deployment credentials
```

Top paths: credential recovered from Git history; request with another school's object ID; forged privileged action; stale publication/moderation cache; expensive uncached reads; malicious uploaded PDF; compromised browser script stealing persisted tokens. The latter is an impact path, not a demonstrated XSS finding.

Important boundary: `supabasePlatform` and the scoped query proxy use service-role access. RLS does not automatically protect these direct reads. `src/lib/supabase.ts:57–105` adds school filters; the separate `tenant_rpc` gateway executes business functions with restricted tenant authority. Both paths require regression coverage.

## 4. Detailed findings and proposed fixes

### S01 — Sentry auth token remains recoverable from Git history

- **Severity/mapping:** High, medium likelihood × high potential scope-dependent impact. CWE-798/CWE-200; OWASP A02 Security Misconfiguration and A07 Authentication Failures; API8 Security Misconfiguration where applicable; ASVS configuration/secrets controls.
- **Evidence:** Historical `.env.example`, initial commit `14539b40`, line 25, contains `SENTRY_AUTH_TOKEN` with a Sentry token prefix and non-placeholder value. Its removal in a later commit does not remove earlier Git objects. The pattern scanner found the corresponding reachable blob. The value is deliberately omitted. No evidence that `suggfeed-vercel.env` was committed was found.
- **Attack path:** Someone able to read the affected repository history can recover the token and attempt operations permitted by its original Sentry scopes. Repository public visibility, revocation and actual token permissions were not queried. Do not infer current compromise or universal production access.
- **Fix:** Revoke this token in Sentry immediately unless existing revocation evidence identifies it. Create a replacement limited to the required organization/project/release scopes only if still needed; update the relevant secure Vercel/GitHub secret bindings and rebuild affected releases. Review Sentry token activity/access. Coordinate any history rewrite only after revocation; never silently force-push shared history. Add a provider-aware secret scanner over history and CI, with redacted output, and push protection where available.
- **Configuration:** Expand ignore rules to `.env*` and `*.env`, with deliberate exceptions for sanitized `.env.example`; the current `.gitignore:4–11` does not match a filename such as `suggfeed-vercel.env`. Ignore rules do not remove already tracked files or replace scanning.
- **Safe verification:** Confirm revoked status in Sentry's own token UI/audit records; do not test this historical credential against third-party APIs. On a disposable repository, seed a synthetic scanner fixture, expect a blocked commit/CI job and no printed secret. Scanning this repo should report only a documented revoked historical credential, not active secrets.
- **Regression check:** Run a pinned secret scanner in PRs and periodically over reachable history. Record narrowly scoped exceptions by historical fingerprint only after revocation, rather than blanket-ignore `.env.example`.
- **Effort/risk:** S for revocation/scanner, M for coordinated history cleanup. Release/source-map uploads may fail until replacement bindings are updated.
- **Rollback:** Fix the replacement secret scope/configuration. **Never restore the exposed credential.** Retain backups and a collaboration plan before any history rewrite.

### S02 — Per-process caches continue serving removed content on other instances

- **Severity/mapping:** Medium, medium likelihood × medium confidentiality impact. CWE-863/CWE-524; OWASP A01 Broken Access Control; API1 Broken Object Level Authorization when a now-disallowed object is returned; ASVS authorization/caching.
- **Evidence:** `src/lib/data.ts:15` uses a module-local Map. `invalidateCache` at line 45 touches only that process. Single-idea content is cached for 5 minutes (lines 203–219), comments for 1 minute (223–236), feed rows for 30–120 seconds (192). `src/routes/api.ts:198–213` changes status and invalidates locally. `src/routes/community.ts:52` also invalidates locally. `src/routes/idea.ts:28–42` serves cached data without a fresh publication check. School status/publication access is rechecked by school resolution, but that does not recheck each idea/comment's moderation state.
- **Attack path:** A visitor loads a published idea via server instance A. Staff remove/reject it through instance B. A can return its cached content until TTL expiry. A withdrawn comment can similarly remain visible. This does not establish cross-school cache leakage; keys include school ID/version.
- **Fix:** Make moderation visibility authoritative in every public response. Simplest interim patch: bypass caches for individual idea/comments and other moderation-sensitive payloads; do not remove only the detail cache while feed cards still expose full descriptions. For preserved performance, use a school content-generation counter incremented in the same database transaction as every publication/hide/delete/merge. Fetch that current counter during existing school resolution and include it in all public data cache keys. Every supported write path, job and authorized manual change must maintain the generation; failure to read it must not serve unchecked content. Continue using current school publication/membership checks.
- **Safe verification:** On staging, use two independent app processes and synthetic distinctive text. Warm A; reject/hide through B; request A's detail, comments, feed and roadmap. Secure: removed text is absent immediately, with correct 404/filtered results. Vulnerable: A still returns it. Also check restored visibility and concurrent writes. No production moderation probe was run.
- **Regression check:** Two-instance integration test covering idea rejection, comment hiding, merge, deletion and generation increments. Include default and customized school versions.
- **Effort/risk:** S for temporary uncaching, M for atomic shared generation. More database reads until cache design is replaced; new generation triggers need load/deadlock review.
- **Rollback:** Roll back generation-specific code while leaving sensitive caches disabled. Do not restore stale-cache exposure merely to recover latency.

### S03 — Leaked-password protection is disabled

- **Severity/mapping:** Medium, medium likelihood × medium account impact. CWE-521; OWASP A07 Authentication Failures; API2 Broken Authentication; ASVS password security.
- **Evidence:** The current configured Supabase project's security advisor returns `auth_leaked_password_protection`. Client reset only requires 8 characters in `src/client/auth-callback.ts:71`; client checks do not establish the provider's effective password policy.
- **Attack path:** A person can select a known compromised password, increasing credential-stuffing exposure. Staff MFA reduces staff impact but does not prevent ordinary student account compromise. Brute-force settings, CAPTCHA and provider lockouts remain unconfirmed.
- **Fix:** Enable leaked-password protection in Supabase Auth settings if supported on the plan. Configure provider-enforced minimum length and a practical passphrase policy for signup/reset, consistent client messaging and provider Auth endpoint rate controls. If the feature is unavailable, record the limitation and adopt reviewed provider-supported compensating controls; do not send plaintext passwords through an ad hoc school backend or claim a client-only check fixes it. Retain MFA for staff/operators.
- **Safe verification:** In a separate Auth project with disposable accounts, verify a provider-documented compromised-password example is rejected for both signup and reset; a unique strong password succeeds. Re-run the advisor. Do not try candidate passwords against real accounts.
- **Regression check:** Mock/provider-contract checks for consistent signup/reset errors, plus a staging smoke check after Auth configuration changes. Store policy configuration evidence without passwords.
- **Effort/risk:** S if supported, M if provider/plan change is needed. Existing users can face password reset friction; changes generally govern new password choices, not automatic account revocation.
- **Rollback:** Restore the previous length/UX configuration only if necessary; retain leaked-password rejection where possible and document temporary compensating controls.

### S04 — Expensive reads lack a distributed pre-database abuse boundary

- **Severity/mapping:** Medium; medium likelihood × medium availability/cost impact absent external mitigation. CWE-400/CWE-770; OWASP A06 Insecure Design; API4 Unrestricted Resource Consumption; ASVS resource controls.
- **Evidence:** `shared-rate-limit.ts:9` skips GET/HEAD/OPTIONS. Express rate limiters use the default instance-local store (`server.ts:155–179`). They are applied to `/api` after session and identity database work (`server.ts:198–215,274–277`). HTML school/feed/idea reads do not use the shared read budget. Search/large offsets can miss caches (`feed-filters.ts:12`, `data.ts:162–176`). Write budgets themselves are shared and fail closed; this finding does not say they are absent.
- **Attack path:** An anonymous or ordinary signed-in actor varies search/offset requests across instances. Auth/session/registry/query work occurs repeatedly and can exhaust the small database or function budget. Large-volume exploitability depends on actual WAF/rate controls; none was asserted absent.
- **Fix:** Confirm existing Vercel edge protections first. Add canonical-path read limits for school pages, search, counts, navigation prefetch and downloads before session/DB work where possible. Use a distributed store outside the already stressed primary database, verified proxy-derived client identity, bounded search/offsets and concurrency/timeouts for expensive work. Add user-level limits after authentication. Exempt authenticated internal jobs only after validating their dedicated bearer secret; do not expose a public bypass header. Keep database membership/permission checks authoritative.
- **Safe verification:** With a small staging fixture, cross two app instances and exceed a deliberately low staging threshold using bounded requests. Expect a shared 429 with Retry-After, bounded database calls and continued ordinary navigation. Test invalid session cookies, search variation, alternate path casing and IPv6 grouping. Do not load-test production.
- **Regression check:** Cross-instance read-limit tests and mock query-call counters proving rejected traffic does not start session/provider reads. Confirm trusted proxy behavior in the actual hosting chain.
- **Effort/risk:** M. Overly broad IP thresholds can block an entire school behind one NAT; deploy per-path/account budgets and measure false positives.
- **Rollback:** Relax specific thresholds or roll back the edge rule; retain hard resource bounds. Never remove authorization or trust arbitrary forwarded IP headers.

### S05 — Retention configuration has no demonstrated execution/cleanup path

- **Severity/mapping:** Medium, medium likelihood × medium privacy/storage impact. CWE-459/CWE-359; OWASP A06 Insecure Design; API9 Improper Inventory Management for stale operational paths; ASVS data protection.
- **Evidence:** `202610100001_web_sessions.sql:11` says delete expired rows daily. `session-store.ts:26–28` deletes an expired session only when that ID is requested again; abandoned IDs remain. `apps/web-express/vercel.json` schedules only customization cleanup. School `retention_days` is stored (`202610160003_school_onboarding.sql:22`) but no complete executing retention worker was found. `supabase/functions/archive-old-submissions/index.ts:1–3` is retired and returns 410. Existing compliance documentation explicitly leaves retention/rights execution open. An external scheduler/manual process might exist and has not been supplied.
- **Attack path:** Accounts/session churn accumulates encrypted rows and stale records; private school content can remain beyond an approved schedule. Encryption lowers plaintext exposure but does not satisfy retention or bound storage. This is not proof that a regulator deadline has already been breached.
- **Fix:** First approve a per-school schedule, legal holds, rights handling and backup expiry. Add a service-only bounded daily session sweep, for example delete expired IDs selected by `expires_at` with `LIMIT 1000` and repeat within a time budget. Implement a separately reviewed tenant-aware retention worker with dry-run mode, explicit foreign-key/storage handling, idempotent batches, audit counts and legal holds. Merely setting `retention_days` must not be presented as an enforced deletion guarantee. Confirm or replace any external scheduler before duplicating jobs.
- **Safe verification:** In a disposable project, seed synthetic expired/unexpired sessions and retained/held/eligible school records; dry run must identify exactly eligible rows. Execute a bounded batch, verify held/other-school/current rows and account permissions remain, confirm attachment cleanup, then exercise restore from a sanitized backup. No deletion was performed here.
- **Regression check:** Date-boundary/legal-hold/isolation tests, bounded cleanup and retry tests, plus an alert on cleanup lag and expired-row growth.
- **Effort/risk:** S for session sweep, L for full school retention. Incorrect retention can irreversibly destroy accounts, evidence or protected records.
- **Rollback:** Disable the job and preserve audit evidence. Restore only from a verified backup with rights-request suppression and tenant boundaries rechecked; deletion has no simple code rollback.

### S06 — Valid-looking PDFs are released without a malware verdict

- **Severity/mapping:** Medium; low-to-medium likelihood (authorized staff upload) × potentially high endpoint impact. CWE-434; OWASP A06 Insecure Design; API8 Security Misconfiguration where the file pipeline is misconfigured; ASVS file handling.
- **Evidence:** `progress-evidence.ts:128–133` accepts declared PDFs with header/EOF framing and explicitly says this is not a malware scan. `finalizeEvidence` makes them ready/publishable. `evidenceDownload:186–192` issues an authorized 60-second download URL. Private buckets, authorization and forced attachment download reduce exposure; they do not neutralize a malicious document opened by a recipient. No external scanning pipeline was provided.
- **Attack path:** A malicious/compromised staff account uploads a harmful but correctly framed PDF that later reaches a recipient. A PDF exploit or harmless upload producing script execution was not demonstrated, and signature checks alone do not prove a file malicious.
- **Fix:** If there is no equivalent external scanner, temporarily reject **new** PDF reservations/finalizations while preserving authorized access to historical files. For continued PDF support, quarantine uploads, scan in an isolated bounded worker, store a verdict/hash and scanner version, and require a clean verdict atomically before ready/publication/download. Recheck existing ready PDFs or keep them quarantined until reviewed. Do not send private documents to a public scanning service without a lawful vendor arrangement.
- **Safe verification:** On staging, use a harmless scanner test fixture under its documented procedure or mock verdicts. Rejected, failed, pending and timed-out scans must never become downloadable; clean fixtures must retain their owner/tenant restrictions. Do not use real malware or students' documents.
- **Regression check:** Clean/pending/infected/timeout state tests, hash binding, retry/idempotency and cross-tenant quarantine tests. Forced download and 60-second URL expiry remain covered.
- **Effort/risk:** S to pause new PDFs, L for scanning. Pausing affects staff evidence workflows; scanning adds queue/vendor costs and latency.
- **Rollback:** Pause PDF uploads if the scanner is unhealthy; preserve private existing objects. Never change scan failure into automatic approval.

### S07 — Trigger functions have unnecessary client execution privileges

- **Severity/mapping:** Low defense-in-depth issue, not a proven privilege escalation. CWE-250; OWASP A02 Security Misconfiguration; API8; ASVS least privilege.
- **Evidence:** Hosted catalog grants anon/authenticated EXECUTE on `handle_new_user()` and `handle_user_email_updated()`. Both return **trigger**, have `search_path=public`, and are defined in `202609280011_profiles_email_and_student_search.sql:13,29`. The security advisor labels them callable RPCs, but PostgreSQL trigger-returning functions cannot be called as ordinary user functions; the warning alone does not establish an RPC exploit. No functions without explicit search paths were found.
- **Fix (additive migration, proposed only):**

```sql
REVOKE EXECUTE ON FUNCTION public.handle_new_user()
  FROM PUBLIC, anon, authenticated;
REVOKE EXECUTE ON FUNCTION public.handle_user_email_updated()
  FROM PUBLIC, anon, authenticated;
ALTER FUNCTION public.handle_new_user() SET search_path = pg_catalog, public;
ALTER FUNCTION public.handle_user_email_updated() SET search_path = pg_catalog, public;
```

- **Do not touch:** Keep the intentional authenticated EXECUTE grants for `school_has_role(uuid,text[])` and `school_is_member(uuid)`. Their source derives the subject from `auth.uid()` and their use in registry/membership RLS is expected. Do not replace server-only tables' deny-by-default posture with permissive `USING (true)` policies just to silence INFO notices. Do not expose `tenant_rpc` to anon/authenticated.
- **Safe verification:** Apply only to a staging database; verify existing Auth signup/email-sync triggers still create/update the profile, clients cannot directly execute the helpers, and roster policies still work. Inspect actual trigger owner privileges first.
- **Regression check:** Catalog allowlist for intended client-callable definers, explicit search paths and service-only mutation RPCs; trigger integration tests.
- **Effort/risk:** S. Unusual provider trigger execution privileges need staging confirmation; changing function bodies or owners is unnecessary.
- **Rollback:** Restore only a specifically required execution grant demonstrated by staging; do not broadly grant PUBLIC. Restore prior search_path only if a measured compatibility issue requires it.

## 5. Fix order and release decisions

1. **Now:** establish S01 revocation and inspect Sentry activity. No history rewrite before revocation and coordination.
2. **Under one hour candidates:** enable supported leaked-password protection; tighten secret-file ignore rules; add a pinned secret-scanning gate; confirm edge protections and scheduler ownership; prepare S07's small migration. These are estimates, not claims of fixes applied.
3. **Before real-school expansion:** remove stale moderation exposure (S02), demonstrate read-abuse protection (S04), establish session/retention operations (S05), and scan or pause PDFs (S06). Confirm actual monitored rights/incident channels and an isolated recovery exercise.
4. Create separate staging projects with synthetic users. Then verify all tenant and privilege boundaries through the deployed browser/API/RPC/storage paths, not only local database fixtures.
5. Preserve current school grants, policy approval/MFA requirements, private buckets and role separation. A UI issue is not justification to bypass these gates.

**Before the next production deployment:** resolve or explicitly record S01 revocation; scope whether that deployment expands school access, PDF uploads or cached public data. If it does, S02/S04/S06 need the corresponding mitigation and staging evidence first. S03/S05 require provider/operational ownership and an agreed closure date before real-school expansion. Routine unrelated fixes do not justify erasing data or weakening authorization.

**Later hardening:** S07, CI action pinning, wider dependency/native scans and measured index tuning. Backup/restore and incident ownership are release evidence requirements, not optional later work if real school data is being onboarded.

## 8. Incident response and rotation checklist

- Appoint an incident lead and school/privacy contacts; retain timestamps in Manila time with UTC equivalents in technical logs.
- Preserve restricted evidence without copying secrets into tickets. Identify affected credential, scopes, sessions, schools, data categories and exposure window.
- Revoke the historical Sentry token; rotate only actually implicated provider credentials. For a service-role leak, rotate/revoke through the project's supported key controls and update secure deployments; the management token and database credentials have separate revocation paths.
- If session integrity/token theft is implicated, revoke provider sessions and invalidate server sessions through an approved bounded operation. Rotating `SESSION_SECRET` invalidates cookie signatures **and** the encrypted payload key; plan clean session-store disposal and forced sign-in rather than trying to decrypt old rows with the new key.
- A Supabase JWT may remain valid until expiry depending on provider revocation behavior. Confirm actual provider semantics; do not promise instant access-token revocation from browser logout alone.
- Contain with targeted feature/credential disablement. Do not delete the database as a substitute for containment or forensics, and do not remove tenant/MFA controls during recovery.
- Coordinate school/controller/processor notification obligations with legal/DPO staff. RA 10173 and NPC notification triggers/deadlines require current legal assessment; no automatic external notification was sent or is authorized by this report.
- Restore only from a known-good isolated rehearsal, reapply rights requests/holds and rotate compromised credentials; verify affected tenants before reopening. Review root cause, alert quality and corrective ownership.

## 9. Unreviewed areas, rejected assumptions and manual assessment

- No real Google login, password recovery, MFA enrollment/recovery, email delivery, signed upload/download, cross-school production request or production load test was performed.
- No provider credential was replayed; no active Sentry token validity assertion is made. Pattern-only scanning can miss secrets in unsupported encodings/formats or outside reachable Git history.
- No external WAF/branch/backup/monitoring control is assumed absent. No legal readiness certification. Current provider JWT/cookie/logout behavior needs deployed end-to-end evidence.
- No SQL injection, exploitable XSS, cross-school row escape or staff privilege escalation was confirmed in the reviewed paths. That statement is bounded by source sampling, local fixtures and catalog metadata, not proof of absence.
- Browser Auth persists tokens (`src/client/auth.ts:5–6`); HttpOnly Express cookies do not make those browser tokens HttpOnly. This increases XSS impact but is not itself a demonstrated XSS flaw. A server-only auth/BFF migration would require a separate OAuth/MFA/recovery design and should not be added casually during this audit.
- PDFs remain risky even as attachment downloads; historical authorization does not substitute for scanning. Conversely, no malware was demonstrated, so this is a documented release-control gap.
- Server-only RLS-without-policy notices are expected deny-by-default. `tenant_rpc_catalog` lacks RLS but has no client privileges in source/readback. The self-subject role helpers are intentional. Keep these boundaries; do not loosen grants to clear warnings.
- Performance warnings need actual query plans/traffic. The duplicate draft index can be reviewed, but constraint-owned/composite-FK indexes must be preserved. `votes` lacking a primary key is not evidence that its current uniqueness/business constraints permit double voting.
- No AI inference/tool feature was found in the deployed Express request paths reviewed. Sentry build tooling and installed coding skills are not an in-product AI feature. If AI is introduced, review prompt isolation, tool permissions, rendering and quotas separately.

Recommended human penetration-test scope: disposable multi-school deployment; each role and anonymous ownership capability; service-role versus tenant-executor boundary; hosted RLS/RPC/storage grants; OAuth/PKCE/reset/MFA/session revocation; editor frame and upload pipeline; stored/DOM injection; CSRF and proxy/canonical-origin handling; two-instance cache races; consent/digest/invitation replay; bounded rate-limit bypass attempts; restore and deletion workflows. Include a school's DPO/legal reviewer for privacy notices, minors and processing contracts.

## 11. Attack-by-attack assessment

“Defenses observed” describes specific controls in source or read-only metadata. It does not mean the whole attack family has been eliminated. All active verification proposed below belongs in disposable staging; this extension performed additional source inspection only, with no new hosted probes or tests.

### Attack 1 — DDoS, bots, slow clients and denial of wallet

- **Applies:** Yes. Public school navigation/search, provider signup/reset/OTP, uploads and invitations can consume compute, database, storage, bandwidth or email quota. No in-product AI or SMS delivery path was identified; their spend risks are not asserted applicable.
- **Defenses observed:** 512 KB JSON/form bounds (`src/server.ts:189–190`); instance API/write/auth limits (`:155–179`); shared IP/account/school write budgets (`src/lib/shared-rate-limit.ts:7–46`); feed page/search bounds (`src/lib/feed-filters.ts:11–12`); private upload reservations and byte/pixel limits (`src/lib/school-images.ts:4–22`); invitation transport timeout/idempotency (`src/lib/invitation-email.ts:30`). CSP permitting Turnstile does **not** establish CAPTCHA enforcement.
- **Protection/gap:** Partial; S04 is Medium. WAF/CDN connection protection, bot rules, hidden-origin requirements, provider Auth email/OTP rate controls, database statement timeouts, actual peak traffic and hard spend caps need confirmation. In particular, browser Supabase signup/reset calls do not pass through the Express `/auth` limiter. Signed upload URLs also bypass Express body limits and depend on Storage restrictions/reservations. A daily budget alert is not a hard spending cap.
- **Fix:** Apply S04's distributed pre-database boundary; set provider-supported Auth delivery limits/CAPTCHA, storage quotas and spend limits with owners. On Vercel, inspect edge/origin routing before proposing a generic “hide origin IP” fix. For any self-hosted origin, enforce ingress through the intended proxy and set connection/header/body timeouts there; use application request/processing deadlines as well. Add an image-processing timeout to the school image path consistently with the evidence path's existing 8-second Sharp timeout (`src/lib/progress-evidence.ts:136`), after staging compatibility review.
- **Detect/verify:** Monitor edge requests/rejections, endpoint/user/school budgets, CPU/query time, function duration/concurrency, uploaded bytes, provider email counts and spend slope. In staging, bounded low-threshold cross-instance tests should yield 429 before expensive work. Slow-client tests belong on an isolated deployment with explicit connection limits, not production. No flood resistance was measured.

### Attack 2 — SQL injection, including blind and second-order paths

- **Applies:** Yes, input reaches PostgREST filters and SQL RPCs.
- **Defenses observed:** Value-bound Supabase builders; fixed sort selection (`src/lib/data.ts:170–171`); escaped search metacharacters (`:81–89`); gateway function catalog, argument allowlist, metadata-derived types, quoted identifiers and bound JSON argument (`supabase/migrations/202610160002_tenant_isolation.sql:244–282`). The restricted `tenant_executor` role is separate from the service-only entry point.
- **Protection/gap:** Parameter/identifier controls are present in reviewed paths; no exploitable SQL injection was confirmed. `sanitizeSearch` constructs PostgREST filter grammar and needs parser-level coverage; escaping is not by itself a proof against every grammar combination. Service-role direct reads remain a high-trust path. Database statement timeouts were not read back. No blind/time-based or second-order campaign was run.
- **Fix:** Preserve bound values and allowlisted metadata; do not accept caller SQL, table names, function names outside the catalog, or freeform ORDER BY. Extend search filter tests with inert punctuation/unicode cases and stored names later reused in search/export. Where grammar ambiguity exists, move the search to a typed, tenant-scoped RPC with bound parameters rather than adding ad hoc escaping layers. Retain generic error responses (`src/server.ts:308–319`).
- **Detect/verify:** Alert on validation/SQLSTATE error spikes using redacted code/endpoint metadata, never full queries containing PII. In staging, assert fixed result scope and unchanged query structure for syntactically awkward inputs; rejected input must not reveal SQL errors or alter another tenant. Timing variance alone is insufficient evidence of blind injection.

### Attack 3 — Stored, reflected and DOM XSS

- **Applies:** Yes. Idea text, comments, school customization, names and links render into pages and client-generated markup.
- **Defenses observed:** Eta output escaping; `textContent` for drawer titles/descriptions (`src/client/idea-detail-drawer.ts:155–156`); escaped comment author interpolation (`:304–312`); staff roster escapes (`src/client/admin-staff.ts:89–99,243–251`); HTTPS/no-credentials link validation (`src/lib/school-customization.ts:29`); self-hosted scripts/no inline executable attributes (`src/server.ts:103–109`); frame origin/source/sequence checks (`src/client/school-studio-frame.ts:35–40`, `src/client/school-customization.ts:37`).
- **Protection/gap:** Multiple defenses observed; no exploit confirmed. `innerHTML` and trusted fragment replacement still require complete source-to-sink review across all client features. CSP is defense in depth, not a sanitizer. Persisted Supabase browser tokens (`src/client/auth.ts:5–6`) increase the impact of any future same-origin script injection.
- **Fix:** Keep untrusted content in text/escaped attribute contexts, centrally validate URLs, and restrict `innerHTML` to reviewed static templates/escaped values. Do not enable arbitrary school HTML/CSS/scripts or loosen CSP for the editor. If rich text is added, use a maintained allowlist sanitizer with explicit link/image policy rather than regex removal of dangerous tags.
- **Detect/verify:** In staging, use harmless distinctive text/attribute/URL fixtures across save/reload, moderation, emails and previews; verify the DOM contains inert text and no executable nodes/handlers. Collect CSP violation metrics with data minimization; inspect unexpected script changes and authentication anomalies. No exploit payloads or production content were submitted.

### Attack 4 — IDOR, cross-tenant access, mass assignment and privilege escalation

- **Applies:** Yes; highest-impact application boundary.
- **Defenses observed:** Registry and active membership resolution (`src/lib/school-context.ts:15–39`); fixed school stamping/filtering and forbidden school ownership updates (`src/lib/supabase.ts:54–91`); scoped composite ancestry/RLS (`202610160002_tenant_isolation.sql:42,60–76`); catalog actor binding (`:247–264`); role/MFA checks (`src/routes/schools.ts:19–50`); private answer/file ownership (`src/routes/school-submissions.ts:20–29`). Hosted tables/buckets/grants were inspected and local A/B fixtures passed within their stated scope.
- **Protection/gap:** Boundary controls observed; full deployed route/RPC/storage coverage remains unverified. S02 is a confirmed stale-authorization risk after moderation. Direct service-role builders rely on application checks and cannot inherit the restricted role's RLS merely because a helper is called “public.”
- **Fix:** Implement S02, retain the lowest-layer tenant constraints/RLS/gateway, and extend negative tests across every current route and new customization feature. Never promote a request's `role`, `user_id`, `school_id` or a cached UI permission into authority. Keep server-only tables deny-by-default; `tenant_rpc_catalog` is the documented no-RLS/no-client-grant exception, not an anonymous data source.
- **Detect/verify:** Log redacted authorization denials, unexpected platform grants and cross-school ID attempts. Staging role matrix must deny read/change/delete with another user's/tenant's IDs and must recheck revoked staff in stale tabs. Normal UI hiding is insufficient evidence.

### Attack 5 — Brute force, stuffing, enumeration, session/JWT/reset/OAuth attacks

- **Applies:** Yes.
- **Defenses observed:** Provider `getUser` verification before trusting access tokens (`src/routes/auth.ts:32`); session regeneration on identity change (`:39–40`); encrypted server payloads (`src/lib/session-store.ts:10–51`); Secure/HttpOnly/SameSite=Lax production cookie (`src/server.ts:205–209`); PKCE and explicit callback handling (`src/client/auth.ts:5–15`); staff assurance from a provider-verified token (`src/lib/auth-assurance.ts:4–12,25–46`); confirmed emails for joining/invitations; shared Express auth mutation budget.
- **Protection/gap:** Partial; S03 is Medium. Provider-facing brute-force/OTP/reset email controls, password policy, JWT algorithm/key rotation/expiry/refresh reuse, account enumeration messages, MFA recovery and real OAuth console allowlists need confirmation. `verifiedTokenAssurance` only decodes after provider verification; do not report its lack of local signature checking as an independent JWT bypass. Server signout and provider token invalidation have different semantics.
- **Fix:** Close S03; configure controls on the actual Supabase Auth endpoints, use generic account-recovery messaging, retain session rotation and validated return destinations, and document staff MFA recovery/offboarding. Define reauthentication/session lifetime for sensitive operations from actual risk rather than trusting an arbitrary client assurance claim. Do not claim a `scope: local` browser signout revokes all other sessions instantly.
- **Detect/verify:** Monitor provider auth failures, reset/OTP delivery spikes, anomalous refreshes and MFA resets with privacy-preserving identifiers. Staging checks: wrong signatures, expired/replayed links/codes, changed OAuth destinations, AAL1 privileged requests, switched users and revoked sessions must fail safely; ordinary Google/password recovery must still work. No real-user credentials were tested.

### Attack 6 — CSRF and clickjacking

- **Applies:** Yes, cookie-authenticated actions and an intentional admin preview iframe exist.
- **Defenses observed:** Global `sameOriginOnly` before body/session handling (`src/server.ts:188`), cross-site Fetch Metadata and origin/referer validation (`src/lib/security.ts:10–23`); SameSite=Lax cookie; default `frame-ancestors 'none'` (`src/server.ts:133`) with the private preview's explicit same-origin-only framing/CSP (`src/routes/school-customization-preview.ts:35–39`). Internal GET jobs require a separate bearer secret (`src/routes/school-customization.ts:63–65`, `src/routes/digests.ts:8–11`).
- **Protection/gap:** Defenses observed; no confirmed CSRF/clickjacking exploit. Requests with neither Origin nor Referer are allowed by the middleware, so browser behavior, cookie settings and privileged request content types remain important. No synchronizer-token defense was found. The guard compares with forwarded protocol/Host; proxy/canonical-host integrity and browser same-site sibling-origin cases need deployed verification. Authenticated internal GETs are deliberate cron interfaces, not unauthenticated state-changing navigation.
- **Fix:** Retain current defenses. For sensitive cookie writes, evaluate mandatory trusted-origin checks with a deliberate policy for absent headers or add session-bound CSRF tokens for supported forms. Use a canonical origin allowlist compatible with actual deployment aliases/proxy behavior; do not blindly reject or accept all headerless requests. Keep cron bearer auth independent and never relax global framing for the editor.
- **Detect/verify:** Record counts of origin/Fetch Metadata denials without logging URLs containing capabilities. Staging checks: foreign/sibling origin forms, missing/malformed headers, legitimate multipart/JSON/form submissions, redirects and preview framing. An attacker origin must not mutate an authenticated account or frame normal pages; the authorized studio frame should remain usable.

### Attack 7 — SSRF, redirects, traversal and command injection

- **Applies:** Redirect/path attacks apply; SSRF/command injection depend on introducing a caller-controlled network/shell sink. No such sink was confirmed in reviewed runtime paths.
- **Defenses observed:** Account/security return allowlists (`src/lib/navigation-context.ts:31–35`, `src/lib/auth-assurance.ts:15–22`); school URL prefix rules (`src/lib/school-path.ts:1–8`); private upload paths constrained to school/UUID/purpose (`src/lib/progress-evidence.ts:54–63`); official links validated without being fetched (`src/lib/school-customization.ts:29`); Resend uses a fixed HTTPS host (`src/lib/invitation-email.ts:30`). Domain verification uses bounded TXT resolution for a validated domain (`src/lib/school-domains.ts:13–18`), not an arbitrary HTTP fetch.
- **Protection/gap:** Defenses observed; no confirmed exploit. Redirect/parser encoding edge cases and every old route need staging coverage. Build/tooling shell commands must be assessed separately from application input handling. A valid HTTPS user link may still be deceptive; scheme validation does not establish school ownership of the destination.
- **Fix:** Keep destinations bounded, storage paths generated server-side and commands free of caller interpolation. Do not add remote image/link previews without DNS/IP/redirect/size/time controls and a dedicated egress policy. Show official-link destinations clearly; require institution review for links rather than claiming HTTPS means trusted.
- **Detect/verify:** Monitor unexpected egress destinations and repeated rejected return/path values in aggregate. Staging should keep encoded/confusing paths inside the intended origin/school and deny another school's object path. Use only owned fixture hosts if remote-fetch functionality is introduced; never probe metadata services or third-party targets.

### Attack 8 — Malicious/oversized uploads and unauthorized downloads

- **Applies:** Yes.
- **Defenses observed:** Server-generated UUID/private paths, intent ownership, size/content checks and image re-encoding (`src/lib/school-images.ts:12–28`); byte signatures and 24 MP/8-second evidence limits (`src/lib/progress-evidence.ts:116–144`); download authorization and 60-second URL (`:81–89,186–192`). Readback: four private buckets with size/MIME allowlists.
- **Protection/gap:** Partial; S06 is Medium. PDF framing is not sanitization/scanning. Signed URLs are bearer capabilities until expiry. The school-branding image path has pixel/type limits but no explicit Sharp processing timeout, unlike evidence; no saturation test was performed. Guess-resistant IDs alone are not access control.
- **Fix:** Apply S06's quarantine/scan-or-pause policy; preserve owner/school checks, re-encoding, expiry, immutable final paths, reservation quotas and cleanup. Bound school image processing and concurrent workers. Do not make a bucket public to fix UI download issues or accept uploaded SVG/HTML.
- **Detect/verify:** Monitor validation failures, upload byte/reservation quota, processing time, orphan backlog and denied downloads. Staging fixtures must reject mismatched MIME/size/dimensions, expired/replayed owner intents and foreign-school paths; clean files should still render. Scanner verdict tests use harmless fixtures only.

### Attack 9 — Secrets, source maps and data leakage

- **Applies:** Yes.
- **Defenses observed:** Server-only service key configuration (`src/lib/supabase.ts:34–38`); encrypted sessions; redacted tracking/invitation/query logging (`src/lib/request-path.ts:2–3`, `src/server.ts:149–151`); generic error handler (`:308–319`); private buckets and restricted catalog grants. The current client secret-pattern scan found no service-role JWT/private key match.
- **Protection/gap:** S01 is High and unresolved until revocation is evidenced. Pattern-only scans are incomplete; source-map/debug artifact availability, build logs, all provider key formats, forks and mobile bundles were not fully inspected. An anon/publishable Supabase key is expected client configuration, not equivalent to a service-role secret. Separate environment keys/least privilege are not proven merely because variable names differ.
- **Fix:** S01 plus redacted CI scanning and environment/key inventory. Protect runtime credentials in provider secret stores; constrain source maps to the intended observability access path or intentionally public nonsecret source. Do not put credentials in build-time public variables, diagnostic pages, copied env files or user-facing errors.
- **Detect/verify:** Secret scanner/host push-protection alerts, provider credential usage/audit changes, unexpected artifact access and recurring sensitive-log patterns. Verify bundle/artifact absence with synthetic known markers in a staging build; never publish a real secret to test detection.

### Attack 10 — Supply chain and CI compromise

- **Applies:** Yes; package install/build actions can affect deployed code and secrets.
- **Defenses observed:** Frozen install commands in CI/deploy, committed lockfiles, Dependabot (`.github/dependabot.yml:1–18`), separate protected-environment deployment jobs (`.github/workflows/deploy.yml`), typecheck/test/build pipeline. Express production advisory check returned zero known advisories for the observed lockfile snapshot.
- **Protection/gap:** Partial. CI uses moving action version tags and has no explicit secret/SAST/dependency-security gate in source. Effective GitHub token permissions, branch protection and environment reviewers are unknown. The production-only npm result does not cover dev scripts, malicious packages without advisories, native libraries, legacy dependencies or postinstall effects.
- **Fix:** Pin action revisions, keep reviewed updates/frozen locks, set explicit minimal workflow permissions, separate untrusted PR execution from deployment secrets and add Section 6's scanning gates. Confirm the deployed Express lockfile gets updates independently of the root pnpm lock. Review lifecycle scripts in dependency changes; blanket `--ignore-scripts` is not a safe drop-in fix for required native builds.
- **Detect/verify:** Alert on workflow/lockfile changes, new publisher/lifecycle scripts, altered environments and unexpected artifact provenance. In a disposable PR fixture, confirm scans block seeded harmless findings and fork PRs cannot access deployment secrets. No malicious dependency was installed for this review.

### Attack 11 — Man-in-the-middle and transport downgrade

- **Applies:** Yes for browser-to-app, app-to-provider and recovery/deep-link traffic. Mobile transport cannot be assessed without mobile source/builds.
- **Defenses observed:** Production HSTS and HTTPS upgrade policy (`src/server.ts:135–139`); Secure session/device cookies (`:206`, `src/lib/submission-context.ts:11`); HTTPS-only school links (`src/lib/school-customization.ts:29`); fixed HTTPS Resend transport; release checks reject malformed/noncanonical HTTPS origins (`src/lib/release-readiness.ts:3–9,21–22`).
- **Protection/gap:** Controls exist in source; live certificate validity/renewal, TLS versions/ciphers, HTTP redirects, alternate-domain behavior, origin ingress and server-to-database transport were not independently measured. HSTS is sent only when production mode is active; local source settings are not deployed-header evidence. No MITM or TLS interception was attempted.
- **Fix:** Verify Vercel-managed certificates/renewal and canonical HTTPS redirects for apex/www/approved aliases; prevent insecure direct-origin access if a separate origin exists. Keep provider TLS verification enabled; don't add self-signed exceptions to fix connectivity. Review subdomain compatibility before extending HSTS policy/preload. Do not add mobile certificate pinning without an update/rotation/recovery model and an assessed threat that justifies it.
- **Detect/verify:** Certificate expiry/domain mismatch and HTTPS/header monitoring from an authorized monitor. On staging, verify secure cookies, redirects and mixed-content absence. Provider TLS configuration/read-only diagnostics are preferable to intercepting production users. **Status: needs deployed transport evidence; no confirmed transport vulnerability.**

### Attack 12 — Phishing, compromised admins and insider misuse

- **Applies:** Yes. A legitimate high-privilege account can access sensitive information or change school behavior even without an injection flaw.
- **Defenses observed:** Fresh platform authority (`src/lib/navigation-context.ts:5–10`), current school membership, staff/operator MFA (`src/routes/schools.ts:19–50`), domain proof, reviewed policy/customization transitions and audit events. Membership changes serialize last-admin protection and record prior/new roles (`supabase/migrations/202610160001_school_registry.sql:125–148`). Invitations bind verified email and live inviter authority.
- **Protection/gap:** Partial; organizational identity verification, least-privilege reviews, training, provider console MFA, support verification, recovery and offboarding procedures are unknown. TOTP MFA is useful but not phishing-resistant. An insider with valid authorization is not blocked merely by RLS; read/download auditing and an independent audit sink need evidence.
- **Fix:** Document grant/recovery/offboarding approvals, disable departed memberships/operator access promptly and revoke implicated provider sessions. Prefer provider-supported phishing-resistant authentication for especially sensitive operator/provider consoles where available; do not invent WebAuthn support that the application does not implement. Establish dual approval for destructive bulk operations and independently retained audit evidence, with scoped emergency access.
- **Detect/verify:** Alert on privileged grants, MFA resets, unexpected role/domain/publication changes and unusual sensitive-download volume. Staging should deny a revoked admin from old tabs and preserve last-admin recovery; conduct a nondeceptive recovery/offboarding tabletop. No phishing was conducted and no new real admin was created.

### Attack 13 — Ransomware, destructive insiders and accidental data loss

- **Applies:** Yes. Database/storage deletion, stolen service credentials, operator mistakes and compromised CI can affect all schools.
- **Defenses observed:** Restricted service-only functions, per-school roles, private buckets, immutable publication history and selected relational deletion constraints. These reduce some paths but are **not backup/recovery evidence**. The existing retention/recovery protocol is documented in `docs/compliance/school-release-readiness.md`.
- **Protection/gap:** **Needs input.** Backup encryption, access isolation, separate account/location, retention, PITR entitlement, object-storage coverage, Auth consistency, restore rehearsal, RPO/RTO and ransomware recovery ownership were not verified. S05 concerns retention execution; it must not be misrepresented as a proven backup failure. Version history stored in the same database does not survive deletion of that database.
- **Fix:** Establish least-privilege recovery credentials and independently protected backup retention covering database, Auth identity requirements, private Storage objects and configuration. Define school-aware RPO/RTO and evidence a restore into an isolated project before real-school expansion. Add reviewed approval/hold/dry-run safeguards for destructive actions. Do not delete/restart the current database to “verify” backup availability.
- **Detect/verify:** Monitor anomalous bulk deletes, privilege changes, backup failures and restore age. Rehearse with synthetic data and a known recovery point in a separate project, checking accounts, tenant boundaries, file authorization, rights deletions and application compatibility. Human incident/tabletop review is required. No destructive recovery test was performed.
